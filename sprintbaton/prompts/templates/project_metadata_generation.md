# Project metadata generation (init pass — project index)

{location_guide}

You are running SprintBaton's **init pass** at the **project** level. A
project groups one or more git repositories behind a single todolist board (for
example a `frontend` UI repo and a `backend` API repo). Your job is to produce a
combined **project index** that sits *outside* any single repository and explains
how the repositories compose the product — and, crucially, points every
downstream model at each repository's own `.sprintbaton/info` metadata so it knows
to look there.

The `info` file you write is injected into the prompt of **every** downstream
role, as its first view of the project. For the roles that work without a
checkout — the Router, the Passing Criteria, Spec Classification, Plan
Classification, Repository Scoping and Revision Classification steps — it is the
**only** view: they can never open a repository's own metadata. The roles that do
get a checkout (the Spec Model, the Planning Model, the Coding Model, the Review
Model, the Conflict Resolution Agent) start from it and then read deeper.

From `info` alone a reader must therefore be able to: understand what the product
is, see which repositories exist and what each one is responsible for and holds,
decide which repository(ies) a given task touches, tell whether a task touches an
importance-gated surface, and know that each repository carries its own detailed
internal metadata.

## Never state a filesystem path

**Do not write any clone path or working-directory path into the *content* of
these files.** (The `repos/<repo-id>.md` filenames below are keys inside the
project metadata itself, not locations on disk — those are still required.)
You are running once, at init time; the concrete layout
differs per role and per turn. A role that browses the whole project works in a
task root holding a read-only clone of every repository; the coding, review and
conflict-resolution roles work *inside* one repository's clone, one level deeper,
with no sibling repository checked out at all. Any single path you invent here is
therefore wrong for somebody.

SprintBaton prepends a generated "Where things are on disk (this turn)" section
to this index every time it is used, listing the exact current location of each
repository for the role reading it. Your job is to say **what** each repository
is and **that** each one has its own `.sprintbaton/info` worth opening; the
runtime supplies **where**. Refer to a repository by its title and id, never by a
directory.

## Determinism (produce the same structure regardless of which model you are)

This contract is rigid so any capable model — small or large — produces the same
file set and the same structure for a given project. Only the depth of the facts
should vary with model capability, never the shape. Emit exactly the files
described below, named exactly as specified, ordered as specified.

## Files to emit

Emit these files (paths are relative inside the project metadata directory):

- `info` — the index file (no extension). Contract below. **Always emit it.**
- `repos/<repo-id>.md` — one file per member repository (use the repository id
  given in the input, verbatim, as the filename stem). Contract below.

Do not emit anything else. Do not attempt to re-document the internals of any
repository — that already lives in each repo's own `.sprintbaton/` (generated by
the per-repository init pass). Your job is the cross-repository map only.

## The `info` index file

Exactly this shape:

    version: v1

    # Project: <project title>

    <2–4 sentence overview of what the product is and how the repositories
    compose it — e.g. "a React single-page app (web-frontend) talking to a
    FastAPI backend (web-backend) over REST".>

    ## Repositories

    - <repo title> (id: <repo-id>, <role>) — <its responsibility in the
      project, then its main surfaces by name, taken from its `info` index: the
      screens, services, entities, API surfaces and features it holds — two to
      four lines>. Detailed internals: this repository's own `.sprintbaton/info`.
    - ... one bullet per repository, in the order they are listed below ...

    ## Importance-gated surfaces

    - <repo title> — `<path of the file in that repository's metadata>`
      [importance: <marker>] — <that file's one-line description>
    - ... one bullet per marked line, grouped by repository in the order
      above, then in the order the lines appear in that repository's `info` ...

    ## How to navigate

    Start from this index to decide which repository(ies) a task touches. Then,
    for each repository you need, open that repository's own `.sprintbaton/info`
    — the "Where things are on disk" section above this index gives its current
    location — for its services, entities, screens, and APIs before acting. A
    single task may span several repositories, and SprintBaton handles each one
    in a separate run with its own pull request.

The `## Importance-gated surfaces` section copies **every** line carrying an
`[importance: auth|payments|migration|core]` marker out of each repository's
`info` index — exactly those lines, never one you judged important yourself and
never one fewer. The Router decides whether a task is important from this list
and has nothing else to go on. When no repository has a marked line, keep the
heading and write the single line `None.` under it.

The per-repository bullet **must** say that the repository carries its own
`.sprintbaton/info` — a downstream model will not think to look inside a
repository's `.sprintbaton/` unless this index tells it to. Name the file, not a
path to it.

## The per-repository files (`repos/<repo-id>.md`)

For each member repository, a compact file:

    # <repo title>

    ## Role
    <what this repository is responsible for in the project — one short paragraph>

    ## Identity
    Repository id: `<repo-id>`. Remote: `<remote, as given below>`.

    ## Internal metadata
    Detailed structure (services, entities, screens, APIs) is in this
    repository's own `.sprintbaton/info` — consult it before editing this repo.

    ## Interfaces with other repositories
    <how this repo talks to the others — e.g. "consumes the REST API exposed by
    web-backend"; or "none" for a standalone repo>

## Existing metadata

Your working directory is the project metadata directory, pre-populated with the
project's **current published index** (empty on a first run). Treat every
existing statement as a hypothesis: check it against the repository information
below, correct or delete what is wrong, keep file names stable, and never
create a second file for a repository that already has one. Emit a
`repos/<repo-id>.md` file for **exactly** the member repositories listed below.
If the directory holds a `repos/` file for a repository that is no longer listed,
name that file in `removedFiles` so it is deleted.
